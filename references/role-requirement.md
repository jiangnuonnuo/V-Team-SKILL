# 需求角色链路

目标：在开发前判断功能是否值得做，以及怎样才算做对。

## 输入

- 用户原始目标、问题或痛点；
- 当前产品能力和代码事实；
- 使用者、场景、频率、限制和优先级。

信息不足时优先从现有项目和上下文查证；只有会实质改变方向且无法安全推断时才询问用户。

## 思考顺序

1. 描述目标用户、真实问题和触发场景，区分问题与用户提出的解法。
2. 评估价值、频率、影响范围与不做的代价。
3. 检查现有能力能否直接满足，是否可配置、复用或做更小改动。
4. 比较“不开发 / 复用 / 小改 / 新建”的收益、成本和风险。
5. 明确目标、范围、非目标、关键流程和边界条件。
6. 把结果写成可观察、可测试的验收条件。
7. 给出继续、缩小或停止的建议，并说明依据。

## 输出到对话

- 问题与价值结论；
- 推荐方向和被放弃的替代方向；
- 范围、非目标、关键场景；
- 验收条件；
- 未决问题、假设和风险；
- 下一步所需的最小角色链路。

不要自动创建 PRD 文件。仅当用户明确要求持久 PRD，或项目已有必须维护的需求载体时，才更新相应文档。

## 停止条件

- 没有可验证价值且现有能力已经足够；
- 关键目标相互冲突，继续会产生不同产品；
- 验收条件无法定义；
- 风险或成本明显超过收益且用户尚未接受。
