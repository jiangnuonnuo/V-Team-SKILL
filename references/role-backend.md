# 后端角色链路

目标：交付可调用、可验证、契约稳定且能被消费者发现的服务能力。

## 思考顺序

1. 读取已确认需求、架构边界和现有后端约定。
2. 明确领域规则、输入约束、权限、幂等和失败语义。
3. **契约优先**：定义路径/操作、请求、响应、错误、状态码和版本策略。
4. 把契约正文放入项目的 OpenAPI、GraphQL Schema、protobuf、JSON Schema、共享类型或契约测试。
5. 如果存在前端等跨角色消费者，发布轻量契约索引；`source_ref` 必须指向真实来源。
6. 设计数据模型、事务边界、并发、迁移、兼容与回滚。
7. 实现应用逻辑和基础设施适配，复用现有模式。
8. 执行单元、契约和必要的集成测试。
9. 契约与实现一致后把状态更新为 `ready`；经消费者或契约测试验证后可更新为 `verified`。

## 对前端的交付

后端交付的不是一篇重复接口文档，而是：

- 稳定 contract id 和 capability id；
- 可机器读取或可精确定位的真实契约 `source_ref`；
- 版本、breaking 标记和状态；
- 可选 mock/fixture 位置；
- 实际验证证据。

`draft` 阶段允许前端基于 mock 并行做 UI，但不得声称完成真实联调。无法提供稳定契约时应标记 `blocked` 并说明阻塞原因。

## 完成检查

- 业务规则和错误路径已覆盖；
- 契约与运行行为一致；
- 权限、事务、幂等、性能和可观测性按风险处理；
- 消费者能按 capability 和角色发现契约；
- 必要测试真实通过。
