# 角色路由

先确定任务路线，再选择角色；不要反过来为了使用角色扩大流程。

## 路线判定

### 问答/分析

满足以下特征：只需解释、评审、排查原因、比较方案或整理需求，用户没有要求改代码。

动作：只读检查和回答。不得创建状态、计划、总结或里程碑文件。

### 快速改动

必须同时满足：

- 需求和预期结果没有歧义；
- 是机械性、重复性或局部低风险变更；
- 不改变公共 API、Schema、持久化数据、认证授权、安全边界或架构边界；
- 不需要新的产品取舍或 UI 方案确认；
- 易验证、易回滚、影响面清楚。

动作：直接由最相关角色实现，做最小充分验证，不写 V-Team 状态。

### 标准功能

任一条件成立：新增用户能力、行为变化、需要产品取舍、需要新 UI 流程、需要前后端协作，或需要选择实现方案。

动作：需求/价值 → 技术方案/架构 → 用户确认 → 角色实现 → 联调/验收。讨论保留在当前会话，不强制写 Markdown。

### 重大改造

任一条件成立：跨多个核心模块、公共协议破坏性变化、数据迁移、安全/权限边界变化、核心架构替换、回滚困难、持续多个会话或用户明确要求里程碑。

动作：走完整标准路线；按需维护紧凑恢复状态；只为重要决策或里程碑引用持久记录。

## 最小角色选择

| 任务特征 | 最小角色链路 |
|---|---|
| 需求仍不清楚或价值可疑 | requirement |
| 仅局部、无行为变化的前端修复 | frontend |
| 仅局部、无公共契约变化的后端修复 | backend |
| 新后端能力，无 UI 消费者 | requirement → backend → qa（按风险） |
| 新页面，已有稳定接口 | requirement → frontend → qa（按风险） |
| 新全栈功能 | requirement → architect（需要选型时）→ backend → frontend → qa |
| 核心架构或协议改造 | requirement → architect → 相关实现角色 → qa |

角色 ID 使用 `<discipline>-<capability-scope>`。一个角色必须对可验收的功能结果负责，不能只负责若干文件。可以由同一 Agent 依次承担多个角色，但切换角色时只加载该角色所需参考和上下文。

## 升级规则

执行中发现以下情况，立即暂停实现并升级到标准或重大路线：

- 需求出现新的业务取舍；
- 必须改变公共契约或数据结构；
- 影响认证、授权、隐私或安全；
- 现有架构无法支持且需要新增边界；
- 验证发现影响面明显超出最初判断。
